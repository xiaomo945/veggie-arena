# 02 · 工程约束与规范

> 这份文档是**写给未来的我们（和 AI）看的**。项目会做几个月，中间会换 AI 会话、会忘了当初为什么这么写。
> 所有规则一旦定下，改动必须走"修改本文档 + 说明理由"的流程。

---

## 0. 为什么要有这份东西

三个真实数据，决定了这些约束不是形式主义：

1. **vibe coding 有硬天花板**：CMU 研究 807 个仓库发现，AI 生成代码的复杂度平均 +41%，而速度增益**两个月后消失**。1400 行的单体 JS 是死路。
2. **单人 + AI 的最大风险是"改不动"**：三个月后想加一个功能，发现牵一发动全身，只能推倒重来。
3. **用户不会编程**：意味着**没有任何人能通过读代码来验证正确性**——只有自动化测试能保护项目。

> 所以核心原则只有一条：**让"不会编程的人"也能安全地推进项目。**

---

## 1. 十条硬规则（违反即视为 bug）

### R1 · 先写需求，再写代码
任何一个功能，先在 `docs/` 或提交信息里写清楚"做什么、怎么验收"，再动手。
禁止"边写边想"。

### R2 · 一次只做一个功能
一个功能 = 一次提交 = 一次测试 = 一次实机验证。
**禁止一口气做完一整批功能再测。**

### R3 · 数值与代码彻底分离
所有平衡数值（伤害、血量、价格、刷怪速率）**只能**出现在 `data/*.json`。
改平衡 = 改 JSON，**不改任何 .gd 文件**。

### R4 · 逻辑层零渲染依赖
`core/` 下的脚本**不允许**引用任何 Node、场景、纹理、输入事件。
它们必须能在 `--headless` 下独立运行并被测试。
> 这是整个项目的生命线：只有这样才能"不打开游戏就知道有没有坏"。

### R5 · 每个 core 模块必须有测试
新增或修改 `core/` 里的任何函数，必须同时写/更新 `tests/test_*.gd`。
没有测试的代码 = 没有写完的代码。

### R6 · 单文件不超过 300 行
超过就必须拆。这是防止 AI 写出"1400 行单体脚本"的最有效手段。

### R7 · 提交信息有格式
```
feat: 新增锅气机制
fix: 修复摇杆变向死区
balance: 第3波刷怪速率 1.4 → 1.2
docs: 更新需求文档 P1 清单
test: 补充武器合成边界测试
refactor: 拆分 Combat.gd
```
提交信息里必须写清楚**改了什么、为什么**。

### R8 · 每完成一个功能，必须导出网页版实机验证
自动化测试只能证明"逻辑没错"，不能证明"好玩"。
用户只看得懂"能不能打开、能不能玩"。

### R9 · 每次可玩版本打 tag
`v0.3` `v0.4` …… 打 tag 后如果后续改坏了，能立刻回滚到上一个能玩的版本。

### R10 · 不许在 main 上直接开发
新功能开新分支（或至少先提交一次可运行版本），验证通过再合入。

## 2. 目录结构（唯一事实来源）

```
veggie-arena/                 ← 仓库根即 Godot 4.3 工程（唯一代码库，工程文件在最外层）
├── project.godot
├── export_presets.cfg        Web 导出预设（产物覆盖写到 web/build）
├── autoload/                 全局单例（游戏一启动就存在）
│   ├── GameState.gd          全局状态
│   ├── Events.gd             事件总线（模块解耦用）
│   └── Data.gd               读 data/*.json，全局只读访问
├── core/                     ★ 纯逻辑层（无渲染，可 headless 测试）
│   ├── Combat.gd / Spawner.gd / Economy.gd / Inventory.gd / Movement.gd / Hit.gd / Weapon.gd
│   ├── Wok.gd                锅气招牌机制纯逻辑
│   └── Run.gd                通关判定 + 结算分
├── data/                     ★ 纯数据，数值只改这里
│   ├── balance.json          全局数值：血量、速度、波次长度、锅气
│   ├── weapons.json          武器表
│   ├── enemies.json          敌人表
│   └── upgrades.json         强化表
├── entities/                 场景 + 表现层脚本
│   ├── Player/  Enemy/  Bullet/
├── ui/                       界面
│   ├── HUD/  Shop/  Screens/  Joystick/
├── tests/                    测试（headless 跑）
│   ├── run_tests.gd          测试入口
│   └── test_*.gd
├── art/                      美术资源
│   ├── icon_weapon_*.png     武器图标
│   └── raw/                  原始/未处理素材（本地，不进 git）
├── docs/                     文档（先写后做）
│   ├── 01_需求文档.md … 04_模块结构与路线图.md
├── web/                      导出产物 + 部署
│   ├── build/                Godot 导出（**不进 git**，唯一在线产物）
│   ├── landing/              落地页（SEO、介绍）
│   └── vercel.json           Vercel 自定义域名配置
├── archive/                  早期原型（只保留，不再改）
│   └── ArenaSurvival_竞技场生存_手机版.html
└── scripts/
    └── check.sh               一键：语法检查 + 跑测试
```

### 依赖方向（只能单向依赖，违反即重构）

```
data/  ←  core/  ←  entities/ + ui/
              ↑
         autoload/
```

- `core/` 可以读 `data/`，**不能**引用 `entities/` 或 `ui/`
- `entities/` 和 `ui/` 可以调用 `core/`，**不能**被 `core/` 调用
- `autoload/` 提供全局访问，但**不放业务逻辑**

## 3. 命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| GDScript 文件 | PascalCase | `Combat.gd` |
| 场景文件 | PascalCase | `Enemy.tscn` |
| 函数 / 变量 | snake_case | `spawn_enemy()` |
| 常量 | UPPER_SNAKE | `MAX_SLOT` |
| 信号 | past_tense | `enemy_died` |
| JSON 键 | snake_case | `"spawn_rate"` |
| 美术资源 | `类型_名称_状态.png` | `icon_bow_lv2.png` |
| 分支 | `类型/简述` | `feat/wok-heat` |
| 标签 | `v0.3` | |

## 4. Git 工作流

```bash
# 1. 开分支
git checkout -b feat/功能名

# 2. 写代码 + 写测试（一次只做一件事）

# 3. 本地自检
bash scripts/check.sh

# 4. 提交
git add -A && git commit -m "feat: 简述（为什么改）"

# 5. 导出网页版 → 实机验证

# 6. 验证通过后合入并打 tag
git checkout main && git merge feat/功能名 && git tag v0.4
```

## 5. 测试要求

### 必测项（每个功能）

| 类型 | 说明 |
|---|---|
| **正常路径** | 功能按预期工作 |
| **边界** | 0、满值、负数、溢出 |
| **回归** | 之前通过的测试仍然通过 |

### 跑测试

```bash
cd godot
/opt/godot/Godot_v4.3-stable_linux.x86_64 --headless --script tests/run_tests.gd
```

### 测试文件的写法（Godot 4.3 的三个坑）

1. `--script` 模式下 `class_name` **不会注册全局类** → 必须用 `const X := preload("res://core/X.gd")`
2. GDScript 数组元素是 `Variant` → 必须显式 `int()` 转换，否则 `:=` 类型推断失败
3. 测试里要手动调用 `_ready()`，不能等引擎回调

## 6. 数值改动流程（用户不会编程，这条最重要）

**用户想改平衡时，正确流程是：**

1. 用户说"第 5 波太难了"
2. AI 改 `data/enemies.json` 里对应的数值
3. AI 跑 `scripts/check.sh` + 跑一次平衡模拟
4. AI 导出网页版，给用户链接
5. 用户实机试玩
6. 满意 → 提交 + 打 tag

**用户永远不需要碰 .gd 文件。**

---

## 7. 美术资产规范

- 格式：PNG（透明底）/ SVG（图标）
- 尺寸：武器图标 128×128，敌人 256×256，角色 256×256
- **必须先确认授权**（商用字体、音效、素材都要授权）
- **AI 生成的美术只用于网页版**；Steam 版走极简风格或真人外包

---

## 8. 定义"完成"

一个功能只有在满足以下**全部**条件时才算完成：

- [ ] 代码已提交，提交信息符合 R7
- [ ] `scripts/check.sh` 全绿
- [ ] 数值只在 `data/*.json` 里
- [ ] 单文件 < 300 行
- [ ] 导出网页版，用户实机验证通过
- [ ] 文档（如需）已更新

---

## 9. 修改本文档的规则

本文档的任何修改都必须：
1. 在提交信息里写 `docs: 修改约束 R3 —— 理由：xxx`
2. **不能因为"这次来不及"就绕过规则** —— 绕过一次，规则就死了
